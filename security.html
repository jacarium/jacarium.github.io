Security

Security and the software supply chain.

As an engineer and DevSecOps Certified AI Security Professional, currently working towards becoming a Software Supply Chain Security Expert, I make security the priority in this app: what you download can be traced back to the exact source and the exact build that produced it, and you can check it yourself.

As of v3.4.8, October 2026. Everything below runs for every release since v3.4.5; earlier releases don't have the full set of attestations.

The OpenSSF Best Practices badge at the passing level, and an OpenSSF Scorecard that's published and updated weekly.

Build and provenance

SLSA Build Level 3 provenance

  • For every installer, the container image and the SBOMs.
  • Built by one reusable GitHub Actions workflow on GitHub-hosted runners.
  • Signed in a separate job that runs no project code, with GitHub artifact attestations (Sigstore).
  • Every attestation is verified before the release is created. A release that doesn't verify is never published.

SLSA Build Level 3 describes how the releases are built, not the app itself.

SBOMs

  • SPDX and CycloneDX, made with Syft, for every installer platform and every image architecture.
  • Attached to each release and attested.
  • For the image, the attested SBOM is a package-level copy, because the full file list is over GitHub's 16 MB attestation limit. Both versions are published.

Reproducible container image

  • Two builds of the same commit produce identical layers, except the RPM database timestamps.
  • A weekly CI job checks this.

The desktop installers aren't reproducible; they're verifiable through their provenance.

Signatures

Signed container image

  • quay.io/zerodayz/jacarium is signed with cosign, keyless, with the SBOM and VEX attached as attestations.
  • No registry secret is stored anywhere: Quay is federated with the workflow's OIDC identity and issues a one-hour token per release.

Signed source

  • Release commits and tags are SSH-signed and shown as Verified on GitHub.
  • Between releases, main is published as signed development snapshots.
  • Repository rulesets block force pushes, deletions and unsigned commits on main and on the release tags.

Attestations attached to every release

  • Each release file has its Sigstore bundle next to it (FILE.intoto.jsonl) with the provenance, and for the installers the SBOM and VEX attestations, so anyone can verify a download, even offline.
gh attestation verify FILE \
  --bundle FILE.intoto.jsonl \
  --repo jacarium/jacarium \
  --signer-workflow jacarium/jacarium/.github/workflows/build.yml

Vulnerabilities and code analysis

VEX with every release

  • An OpenVEX document lists which scanner findings don't affect Jacarium and why, each verified in the code.
  • It also lists which findings have a fix pending.

Continuous vulnerability scanning

  • OSV-Scanner on the lock files on every push.
  • Grype at build time: a fixable High or Critical finding fails the build unless the VEX covers it.
  • A weekly re-scan of the latest release's SBOMs.

Code and workflow analysis

  • CodeQL (security-extended) and the OpenSSF Scorecard, on every push and weekly.
  • actionlint over the CI workflows.
  • ESLint with zero warnings allowed.

Secret and privacy scan

  • The published source is scanned for secrets and private data before every release and snapshot.

Dependencies and the image

Dependency policy

  • Nothing younger than 7 days is installed (npm, pip and Dependabot's cooldown). The rare urgent exception is reviewed and publicly logged.
  • Base images and GitHub Actions are pinned by digest or full commit.
  • Third-party tools are pinned binaries whose checksums and signatures are verified before use.

Container hardening

  • The web server (Caddy) is built from source with a current Go toolchain.
  • Unused runtimes are removed from the base image.
  • The Red Hat UBI base image is pinned by digest.

Reporting and contributing

Reporting a vulnerability

  • Private vulnerability reporting, described in SECURITY.md.
  • An acknowledgement within 3 days, and a fix or decision within 30 days.

Contributing and tests

  • CONTRIBUTING.md covers the contribution process, the coding standards and a test policy.
  • The suite has 280+ automated tests, run locally before every release.

Verify it yourself

The README has the commands: gh attestation verify for the provenance, SBOMs and VEX, cosign verify for the container image, and git verify-tag for the source. Every file is on the Releases page.
